On-Prem Deployment Guide

Architecture, prerequisites, sizing, cost, model delivery, and update mechanics — and the questions to ask before committing to an on-prem POV.

Scope: AWS / EKS GCP (GKE) supported; broader multi-cloud on roadmap Last updated Aug 26, 2026 · onprem-installer @ main
Pre-Discover 2.0 architecture. Everything in this guide reflects onprem-installer as it exists today: straiker-system's Postgres/OpenSearch/Valkey are the only data stores, and there is no dedicated data platform component. Discover 2.0 is expected to change this — treat this as current-state, not a commitment for a Discover 2.0-era POV.

1. What "on-prem" means here

Straiker's on-prem offering is not software the customer installs on bare metal — it's a self-managed deployment into the customer's own AWS account. A phased installer script provisions an EKS cluster (or attaches to one the customer already runs), then installs Straiker's product as a set of Helm releases into it. Everything — compute, data, model weights — stays inside the customer's account and VPC; nothing about inference or detection calls back out to Straiker at runtime.

The installer is public and self-service (a single curl | bash one-liner), but a real deployment is rarely fully self-service on a first POV — an FDE is normally in the loop for AWS IAM/quota issues, AI provider setup, and DNS/edge decisions. This guide gives SEs and FDEs a shared, source-verified picture of what that install actually does, what it costs, and what to check before agreeing to run one.

1.1 Product components

Component (Helm chart)What it is
straiker-systemShared infrastructure: Postgres, OpenSearch, Valkey (Redis), Benthos, the NVIDIA device plugin, and the Karpenter NodePools everything else schedules onto.
straiker-artifactOne-time-per-install mirroring layer: copies Straiker's container images into the customer's own ECR and syncs the model weights the customer actually needs into the customer's own S3 bucket.
straiker-coreShared app layer: the frontend UI, Bifrost (LLM gateway, third-party/maximhq, not a Straiker fork), Dex (OIDC), and Caddy.
straiker-inferenceSelf-hosted model serving. One Helm release (vLLM) per GPU model actually required by the selected products, each pulling weights from the customer's own S3 bucket.
straiker-defendArgus — the detection engine. Installed on every deployment regardless of which products are licensed, because Ascend calls Argus's detection API directly. Can optionally route borderline calls to a frontier LLM (via Bifrost) as a second opinion to cut false positives — its own AI-provider dependency, independent of Ascend (see 2.5).
straiker-ascendIris — automated red-teaming (control plane, probe workers, recon workers, report workers). Installed only if Ascend is part of the deal.
straiker-edgeThin TLS ingress (Caddy) in front of the frontend, Defend API, and Ascend API. Always installed; how traffic reaches it depends on edge type (Section 7).

1.2 Install phases

The installer runs a fixed sequence of phases, each idempotent — re-running is a Helm upgrade, not a reinstall. Only phases relevant to the chosen flags actually execute.

4k8s-preflightConfirms the cluster is reachable, resolves a StorageClass for Postgres/OpenSearch, and — on a customer-supplied cluster — validates the customer's own Karpenter is healthy.
5aws-artifactsProvisions the customer's own ECR mirror repos, models S3 bucket, and IAM roles for the mirroring job.

1.4 Quick start commands

Covers the full lifecycle: install, verify, lock down the default admin, and tear down.

1. Install — self-provisioned EKS cluster

curl -fsSL https://raw.githubusercontent.com/straiker-ai/onprem-installer/dist/install.sh | bash -s -- --install-eks --aws-region us-east-1

1. Install — attach to a cluster the customer already has

curl -fsSL https://raw.githubusercontent.com/straiker-ai/onprem-installer/dist/install.sh | bash

1. Install — non-interactive (all required flags supplied up front)

--straiker-customer-name, --straiker-customer-key, and --products are required either way — the bare commands above just prompt for them interactively. Spell them out for a scripted/FDE-led run:

curl -fsSL https://raw.githubusercontent.com/straiker-ai/onprem-installer/dist/install.sh | bash -s -- \
  --install-eks --aws-region us-east-1 \
  --straiker-customer-name <name> --straiker-customer-key <key> \
  --products defend,ascend --yes

2. Check status

curl -fsSL https://raw.githubusercontent.com/straiker-ai/onprem-installer/dist/install.sh | bash -s -- --status

3. Required — remove the builtin admin

Required, not optional: This has to happen before handing the deployment to the customer — it isn't a hardening nice-to-have. Every on-prem install ships the same static bootstrap login (admin@<domain>) with the same password hash across every install — leaving it enabled means a live credential shared across every Straiker on-prem customer, not a POV-only convenience. Treat it as a blocking item on the install checklist:
  1. Help the customer create their own initial admin user — a local account through the UI, or their OIDC IdP once wired in.
  2. Remove the builtin admin from within the Straiker admin console.
This isn't a CLI flag; it's done in-product, and the step isn't done until (2) is confirmed complete.

4. Pick up new artifacts / models (--rerun-phase)

Whenever Straiker publishes new model weights, container images, or a newer chart/bundle version and it doesn't warrant a full reinstall, re-target just the affected phase(s). --rerun-phase forces an already-"done" phase to run again — most phase state is idempotency-cached in ~/.straiker/install.json and is otherwise skipped on a plain re-run:

curl -fsSL https://raw.githubusercontent.com/straiker-ai/onprem-installer/dist/install.sh | bash -s -- \
  --phase artifacts-sync --rerun-phase

That alone just re-mirrors images/models into the customer's own ECR/S3 — it doesn't roll anything out. To actually move the running model pods onto the new version, chain straiker-inference in the same run (add --chart-version if you're also pinning a specific chart release):

curl -fsSL https://raw.githubusercontent.com/straiker-ai/onprem-installer/dist/install.sh | bash -s -- \
  --phase artifacts-sync,straiker-inference --rerun-phase

5. Uninstall / teardown

curl -fsSL https://raw.githubusercontent.com/straiker-ai/onprem-installer/dist/uninstall.sh | bash
curl -fsSL https://raw.githubusercontent.com/straiker-ai/onprem-installer/dist/uninstall.sh | bash -s -- --destroy-eks --yes
Note: Before running any of these: confirm which AWS account/region the shell's credentials actually point at (there's no dry-run) and have the customer name/key ready — omitting them just means an interactive prompt mid-install, not a skip.

2. Prerequisites

2.1 Tooling (wherever the installer is run from)

kubectl, helm, aws CLI, python3, openssl, curl, unzip, and tofu (OpenTofu, pinned to 1.11.6 — the installer can fetch it itself with --install-tofu). gcloud is only needed on the GCP path.

2.2 AWS account & IAM

  • Standard path (installer provisions the VPC): needs the usual EC2/VPC create permissions (CreateVpc, CreateSubnet, CreateNatGateway, etc.) plus EKS and IAM permissions to stand up the cluster.
  • Bring-your-own-VPC path (--vpc-id + subnet IDs): for accounts whose Organizations SCP blocks ec2:CreateVpc. Only needs ec2:DescribeVpcs, DescribeSubnets, DescribeRouteTables, CreateTags, DeleteTags — but the installer will not create a NAT gateway in this mode, so the customer's private subnets must already have outbound routing.
  • Karpenter's IAM role needs inline CreateInstanceProfile/DeleteInstanceProfile permissions (the upstream terraform-aws-modules/karpenter module doesn't ship these).
  • If AI provider mode is Bedrock: the installer calls bedrock-runtime invoke-model during preflight to catch SCP denials or missing model access before deploying anything.

2.3 Kubernetes

If the customer brings their own cluster instead of --install-eks: Kubernetes ≥ 1.28 (charts declare kubeVersion: ">=1.28.0-0"), a working Karpenter installation with healthy CRDs/controller, and a resolvable default StorageClass. If the installer provisions EKS itself, it defaults to cluster version 1.35.

2.4 Network, DNS, and certificates

  • Bring-your-own-VPC needs ≥ 2 private subnets across ≥ 2 AZs, plus public subnets — all three flags supplied together or none.
  • alb / xalb edge types need an ACM certificate ARN by default, or an existing Route53 hosted zone in the same account to auto-issue and DNS-validate one.
  • tailscale edge type needs a Route53 zone for the custom domain in the same account (cert-manager writes DNS-01 challenge records there), plus manual DNS records the customer adds after install, pointed at the assigned Tailscale IP.

2.5 Secrets & credentials to have on hand

  • Straiker customer name + customer key — required; gates image mirroring and model sync via Straiker's artifact broker, and resolves the account's product SKU.
  • An AI provider is no longer an Ascend-only concern. Defend's Argus can route borderline detections to a frontier LLM as a second opinion to reduce false positives (frontier.enabled in straiker-defend's values, off by default) — enabling it needs Bifrost configured with a real Bedrock and/or Anthropic provider, same as Ascend. The three modes are the same either way: own-keys (customer supplies OpenAI/Anthropic/xAI keys), bedrock (no static keys, but requires Bedrock model-access grants for Claude Haiku 4.5 and Claude Sonnet 4.6 in-region), or trial-key (Straiker-hosted key, capped at 30 days, POC use only).
  • If edge type is tailscale: a Tailscale OAuth client (customer's own tailnet, scoped to tag:k8s-operator) plus a cluster-issuer email for Let's Encrypt.
Flag for SE/FDE: The installer's automatic ai-provider-secrets phase only fires when Ascend is selected. On a Defend-only POV where the customer wants frontier false-positive reduction turned on, nobody automates the Bifrost/Bedrock credential wiring — an FDE has to set it up manually (values override + writing the secret) outside the standard phase flow. Confirm during scoping whether Defend-only means "no AI provider needed" or "frontier is wanted, so plan the manual step."

2.6 GPU capacity

Model serving runs on GPU-backed Karpenter nodes (instance families g4dn, g5, g6e). The installer throttles itself to 4 concurrent model installs specifically to avoid tripping the account's GPU instance quota mid-install — but if the target region's default vCPU/GPU quota for those families is low (a common default for accounts that have never run GPU workloads), the install stalls waiting for nodes Karpenter can't launch.

Flag for SE/FDE: A customer's first-ever GPU workload in an AWS account is one of the most common places a POV install stalls. Request a quota increase for the relevant instance families in the target region before the install date, not during it.

5. How new models get delivered

Models are not pulled from the internet at inference time — they're mirrored into the customer's own account once, then served from there.

  • Straiker maintains a source ECR registry and a source models bucket. During install, the aws-artifacts phase provisions a customer-owned ECR mirror and S3 bucket; the artifacts-sync phase runs in-cluster jobs that mirror ~17 container images and rclone-sync only the model weights the selected products actually need (about 10GB per model) — authenticated via the customer's Straiker customer key against Straiker's artifact broker.
  • straiker-inference then pulls each model's weights from the customer's own S3 bucket via an init container, never from the internet directly.
  • New model releases: Straiker bumps a central image-tags file and re-runs its own lint/propagation tooling, which updates every consuming chart and bumps chart versions. Customers pick these up by re-running the installer against a newer published chart/bundle version — typically --rerun-phase on artifacts-sync and straiker-inference, or a targeted --phase run.
  • Install concurrency for models is capped at 4 simultaneous Helm installs (to avoid GPU quota spikes), which also bounds how fast a large model rollout lands.
  • There's no separate license-key file mechanism — the customer key doubles as the entitlement check (it resolves a product SKU that determines which images/models the install will even attempt).

6. Updates & upgrades

  • Every phase does a helm upgrade --install, so re-running the installer against a newer version is an in-place upgrade, not a reinstall.
  • The installer itself ships as a versioned bundle (installer script + Terraform modules) published to a dist branch; --upgrade-installer forces a re-download of the latest bundle.
  • --chart-version pins/bumps chart versions explicitly (per-model overrides exist too); --phase, --from-phase, and --rerun-phase let an SE/FDE re-target just the phases that changed instead of running the full sequence.
  • Settings like --ai-provider-mode and --edge-type can be changed on a later run. --cloud-provider, --provision-strategy, and VPC/subnet flags are first-run-only and permanent for that install.
  • Progress and configuration live in ~/.straiker/install.json (per-phase status, resolved region/cluster/ARNs/flags); --status renders it as a human-readable summary.
  • Certificate rotation for alb/xalb is a standalone action (--update-alb-certificate) that doesn't require a phase re-run; Route53-validated ACM certs auto-renew and don't need this.
  • Uninstall runs the exact same way as install — curl -fsSL .../dist/uninstall.sh | bash (see 1.4) — not a locally-downloaded script. It reads the same ~/.straiker/install.json state file to know what to tear down; --destroy-eks additionally destroys the cluster and Terraform state bucket and is interactive-by-default (types the cluster name to confirm). nuke-eks.sh is the one exception — a manual, interactive-only escape hatch for teardowns that get stuck (orphaned NAT/LB/IAM), and it deliberately refuses to run via curl | bash.
Flag for SE/FDE: --destroy-eks and nuke-eks.sh are genuinely destructive and nuke-eks.sh deliberately refuses to run non-interactively — factor this into repeated POV teardown/rebuild cycles; it can't be scripted headless.

8. Questions to ask before committing to an on-prem POV

8.1 AWS account & access

  • Is this a fresh AWS account/VPC, or does it have an Organizations SCP that blocks VPC creation? (Determines standard vs. bring-your-own-VPC path.)
  • Who can grant IAM permissions for cluster creation — and how long does that approval typically take in this org?
  • What is the account's current GPU instance quota (g4dn/g5/g6e) in the target region? Has this account ever run a GPU workload before?
  • Is there an existing EKS cluster we should attach to instead of provisioning one, and if so, is Karpenter already installed and healthy on it?

8.2 Networking, DNS, and identity

  • Do they control a Route53 hosted zone for the domain we'll use, or will DNS be handled entirely outside AWS?
  • Is the deployment reachable only internally (VPN/Tailscale/internal ALB) or does it need to be internet-facing?
  • Do they have an existing OIDC IdP they want wired in immediately, or is the built-in bootstrap admin acceptable for the length of the POV?

8.3 AI / model providers

  • Which product(s) are in scope — Defend only, or Defend + Ascend? Don't assume Defend-only means no AI provider is needed: Ascend always needs one (and adds the thanos GPU model), but Defend now can too if the customer wants its frontier LLM second opinion for false-positive reduction turned on.
  • Whichever component needs it: own API keys, Bedrock, or the 30-day trial key? If Bedrock, has the customer already requested model access for the required Claude models in-region?
  • If it's Defend-only with frontier wanted, flag that the credential wiring isn't automated by the installer the way it is for Ascend — budget FDE time for the manual setup (2.5).
  • Any data-residency or model-provider constraints (e.g. no calls to a specific third-party provider) that rule out one of the AI provider modes?

8.4 Scale, timeline, and support model

  • Is this a short evaluation (min strategy is fine) or does it need to demonstrate production-grade resilience (ha/max, multi-AZ)?
  • Who owns the AWS bill for the POV, and is there a budget ceiling we should size the deployment against (Section 4)?
  • Who on the customer side will actually run the installer and hold AWS credentials — their own platform team, or does this need to be FDE-led end to end?
  • What's the expected teardown/rebuild cadence? (Repeated destroy/recreate cycles hit the interactive-only guardrails in Section 6.)
  • Is a security review of the shared bootstrap admin credential and default topology (min strategy) required before sign-off, and by when?

9. Summary: things to flag early

  • min provisioning strategy (the default) is single-AZ and explicitly POC-only — don't let it become the production topology by default.
  • The built-in bootstrap admin login shares the same password hash across every on-prem install. Help the customer create their own initial admin user (local account through the UI, or OIDC), then remove the builtin admin from within the Straiker admin console — don't leave it enabled past onboarding.
  • --cloud-provider, --provision-strategy, and VPC/subnet choices are permanent once set — get these right on the first run.
  • GPU quota is the most common install-day blocker; check it ahead of time, not during the install.
  • Bedrock mode has an AWS-console prerequisite (model access grants) that lives outside the installer entirely — confirm it's done before kickoff.
  • Teardown of EKS/VPC infrastructure is intentionally interactive-only and cannot be scripted headless — plan POV rebuild cycles accordingly.
  • "Defend only" is no longer a reliable shorthand for "no AI provider needed" — Defend's frontier false-positive reduction has the same Bifrost/Bedrock/Anthropic dependency Ascend does, just off by default and not wired into the automatic secrets phase.
  • Everything above is the pre-Discover 2.0 design — there's no data platform component in this architecture today. Don't present this as the long-term architecture in a deal that will land post-Discover 2.0; confirm with product/engineering what's changing before committing to specifics with a customer.
